# Stage 2: Outline

Fix the story on one page before any prose. Read `guides/talk-scripts.md` first.

## 2a: Brainstorm

1. List the decisions the story depends on:
   - **hook**: how the talk opens;
   - **thread**: the one example that returns through the talk;
   - **peaks**: the three moments that carry it;
   - **structure**: acts and their order;
   - **close**: the last line, which answers the opening.
2. For each decision, give 3 to 5 short options, one or two lines each, with a suggested pick and
   why.
3. Write `2-outline/options.md`. The author picks per decision, or combines.

## 2b: Consolidate

1. Build one page from the picks:
   - the one sentence, the thread, the three peaks;
   - the acts;
   - the beat table: ID, type (setup, obstacle, payoff, turn, PEAK), spine line, support, time;
   - plants and payoffs: what each earlier beat sets up and where it is paid;
   - what is cut or held for questions: the **held list**, which later becomes the backups;
   - the **sections** the audience will see named (for a progress tracker), four to seven of them.
2. Give beats stable IDs (`B1`, `B2`, ...). Question stops are beats too, with no words.
3. Make the times sum to the slot at the brief's pace class.
4. Write `2-outline/outline.md`.

## Gates before approval

Run both before showing the outline. A failure here costs minutes; found after the build, it costs
a rebuild.

- **Spine read.** Read the beats' spine lines aloud in order, nothing else. Each must answer the one
  before it or raise the question the next one answers. A line that could be swapped with its
  neighbour without anyone noticing is a list item, not a step: restructure.
- **Time to contribution.** Sum the times up to the first beat where the author's own work appears.
  It must meet the brief's target. If it does not, cut motivation, not the contribution.

## Structure that tends to work

For a talk that proposes something, state what is wanted before what exists: goals, then why they
are hard, then the existing attempts judged against those goals, then the idea. When a requirement
is only revealed after the attempts it judges, the attempts have to be explained twice. Derive each
requirement from the task itself (what the method must do) rather than from a rival's failure.

## Checkpoint

`options.md` (2a), then `outline.md` (2b).

## Done when

The author approves the outline. Tag `global/outline-1`.
